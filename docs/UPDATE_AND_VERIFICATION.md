# Проверка и обновление

## На компьютере

`Verify.cmd` собирает предварительный APK, запускает unit/screenshot-тесты и Android Lint. Журнал сохраняется в `.work/verify.log`.

Снимки сравниваются с сохранёнными эталонами, а не перезаписываются. `RecordSnapshots.cmd` обновляет эталоны явно; применять его после визуального осмотра изменившихся экранов.

После запуска эмулятора выполните `powershell -NoProfile -ExecutionPolicy Bypass -File tools/Run-VisualAudit.ps1`. Это проверяет окна и действия настоящего приложения, включая восемь сравнений диалогов с эталонами. Журнал — `.work/device-tests.log`, изображения — `app/build/outputs/visual-audit` и `app/build/outputs/visual-goldens`. Нужны стандартные размер/плотность AVD и шрифт 100%. Проверки виджета и уведомления запускаются отдельно с `-Tests com.example.SystemSurfaceAuditTest`; перед ними таймер preview должен быть завершён.

`tools/Run-AdaptiveAudit.ps1` проверяет 150/200% шрифта и горизонтальную ориентацию, затем возвращает настройки AVD. `tools/Record-MotionAudit.ps1` записывает таймер и его переходы в обеих темах в `app/build/outputs/visual-audit/motion`. Эти команды работают только с выделенным эмулятором и preview-пакетом; тесты могут создавать и удалять собственные демонстрационные записи.

Для узкой повторной проверки: `tools/Run-AdaptiveAudit.ps1 -Variants landscape`. `tools/Run-EmptyAudit.ps1` создаёт отдельный AVD `TimeSheetPro_EmptyAudit` на `emulator-5582`; тесты отказываются работать с заполненной базой. Они не очищают базу основного preview и не используют телефон. Для снижения нагрузки запускайте эмуляторы по очереди. Снимки пустых состояний — `app/build/outputs/empty-audit`.

`tools/Run-EmptyAudit.ps1 -Audit backup` проходит создание JSON, системное сохранение файла, открытие/отмену панели передачи, отмену и подтверждение восстановления, неверный JSON и неподдерживаемую версию. Использует только отдельный пустой AVD; тест отказывается работать с заполненной базой или активным таймером. Исходные настройки возвращаются, собственные строки удаляются; демонстрационные JSON остаются в Downloads этого AVD. Снимки — `app/build/outputs/backup-audit`. Доступен `-SkipBuild`. Формат не содержит отчёты, файлы и текущий таймер; эта проверка не подтверждает сохранность при обновлении APK.

`tools/Run-NarrowAudit.ps1` проверяет ширину 320 dp при шрифтах 100% и 200%, в обеих темах. Работает только с основным выделенным AVD при плотности 420 dpi; временно задаёт 840×1800 px и восстанавливает прежние размер, шрифт и поворот даже при ошибке. Для готовых APK доступен `-SkipBuild`. Снимки имеют префиксы `narrow100-*` и `narrow200-*`.

Оба адаптивных сценария принимают `-Tests` со списком native-тестов через запятую. Например, `-Tests 'com.example.VisualAuditTest#adaptiveWindows,com.example.VisualAuditTest#receiptDocumentAndRestoration'` дополнительно проходит выбор и просмотр чека при каждом размере/шрифте. По умолчанию выполняется только `adaptiveWindows`.

`tools/Run-VisualAudit.ps1 -Tests 'com.example.ReceiptImageAuditTest,com.example.VisualAuditTest#receiptDocumentAndRestoration'` проверяет JPEG EXIF, ограниченное декодирование PNG/WebP/JPEG и неизменность исходных файлов, затем полный PNG-сценарий системного выбора и оплаты. Тест JPEG использует синтетические файлы в cache, общий viewer и не создаёт отчёты. Снимки JPEG — `jpeg-light-viewer.png` / `jpeg-dark-viewer.png`. Выбор JPEG/WebP через DocumentsUI этой командой не проверяется.

`tools/Run-VisualAudit.ps1 -Tests com.example.DatabaseErrorAuditTest` открывает окно отказа MainActivity на своей базе версии 99 в обеих темах и адаптивных вариантах. Временная подстановка внутреннего Room singleton существует только в тестовом APK; прежний экземпляр возвращается, собственная база удаляется. Схема и файл основной базы не меняются. Требует остановленный preview-таймер, не использует телефон. Снимки — `app/build/outputs/database-error-audit`. Для 320 dp: `tools/Run-NarrowAudit.ps1 -Tests com.example.DatabaseErrorAuditTest -SkipBuild`.

`tools/Run-PdfAudit.ps1` создаёт три печатных примера без обращения к базе: пустой, с крупными числами и с комментарием на нескольких страницах. Проверяет открытие через Android PdfRenderer и выгружает PDF/PNG всех страниц в `app/build/outputs/pdf-audit`. Доступен `-SkipBuild`; используется только выделенный preview-эмулятор. Тест не заменяет визуальный осмотр выгруженных страниц.

`tools/Run-NotificationAudit.ps1` нажимает реальные действия уведомления в SystemUI в обеих системных темах. Проверяет паузу/продолжение и возврат к подтверждению завершения без пересоздания Activity. Работает только на `TimeSheetPro_Pixel9`; требует остановленный preview-таймер и предварительно созданные настройки. Возвращает системную тему, настройки приложения и удаляет свою сессию. Доступен `-SkipBuild`; снимки — `notification-actions-*`. Не проверяет физический телефон или закрытый экран.

`tools/Run-ReducedMotionAudit.ps1` проверяет два сценария таймера в обеих темах при отключённых animator/transition/window animation scales. Использует только `TimeSheetPro_Pixel9` и preview-пакет; исходные настройки восстанавливаются в finally. Доступен `-SkipBuild`. Снимки — `reduced-motion-*`; остальные анимации этой командой не проверяются.

`Preview.cmd` собирает APK и запускает отдельный эмулятор `TimeSheetPro_Pixel9` с Android API 36. Команда установки обращается только к `emulator-5580`; физический телефон не выбирается автоматически. При отсутствии эмулятора требуется аппаратная виртуализация и Android Emulator/Windows Hypervisor Platform.

Локальные JDK и SDK находятся в `.work`. На другом компьютере установите JDK 21+, Android SDK Platform 37.0, Build Tools 36.0.0, Platform Tools, Emulator и образ `system-images;android-36;google_apis;x86_64`, затем задайте `JAVA_HOME` и `ANDROID_HOME`. Gradle 9.3.1 загружается Wrapper с проверкой SHA-256.

Пакет предварительной версии — `com.example.preview`. Он имеет отдельные данные и не читает/перезаписывает общий автобэкап рабочего приложения. Настоящие записи в эту версию автоматически не копируются.

## Обновление рабочего приложения

1. Получить старый APK из исходного проекта AI Studio и убедиться, что это именно установленная версия. Сохранить проект и доступ к прежнему способу подписи.
2. Сделать резервную копию существующей функцией и проверить чтение JSON. Этот формат содержит заказчиков, записи, ставки и настройки, но **не отчёты, файлы, фото и состояние текущего таймера**. Он не является полной страховкой от удаления приложения.
3. Получить исходный ключ или использовать прежний канал сборки. APK не содержит закрытого ключа. Пароли не передавать в чат и не записывать в репозиторий.
4. Для локальной подписи задать `KEYSTORE_PATH`, `STORE_PASSWORD`, `KEY_PASSWORD`, при необходимости `KEY_ALIAS` в своей сессии. Запустить `tools/Build-Update.ps1 -VersionCode N`, где N больше установленного versionCode.
5. Запустить `tools/Test-Upgrade.ps1 -OldApk <старый.apk> -NewApk <новый.apk>`. Скрипт проверяет идентификатор, увеличение versionCode и сертификаты. Он ничего не устанавливает.
6. На отдельном эмуляторе с прежним APK и тестовыми данными проверить установку поверх него с `adb -s <эмулятор> install -r <новый.apk>`. Сравнить записи, заказчиков, ставки, настройки, отчёты, файлы и сохранённое состояние таймера.
7. Только после успешной репетиции обновить телефон поверх существующего приложения. Не использовать uninstall, clear data или флаг отката версии. При несовпадении подписи остановиться.

Production application ID остаётся `com.example`; база — `timesheet_pro_database`, версия схемы — 2. Неизвестная версия базы приводит к сообщению об ошибке, без разрушительного пересоздания. Откат APK к несовместимой схеме не предусмотрен.

## Что проверяют добавленные тесты

- Итоги на 0 / 1000 / 10 000 записей, сохранение хранимых сумм и фильтрация незавершённых записей.
- Местная полночь, смена дня и переход DST; существующее округление сумм.
- Повторное открытие базы v2, сохранение идентификаторов/сумм/путей отчётов, миграция v1→v2.
- Отказ открытия неизвестной версии без удаления строк.
- Снимки четырёх разделов в двух темах и открытие/закрытие ручного ввода.

Эти тесты не заменяют проверку подписи, установку поверх старого APK и проверку реальных вложений на устройстве.

## Измерения производительности

Измерять на Pixel 9 в одинаковом режиме частоты экрана и питания, на старой и новой сборках без отладки, с одинаковыми наборами 0 / 1000 / 10 000 записей. Основные сценарии: холодный запуск, переходы между разделами, прокрутка записей, фильтрация, работа таймера и экспорт.

Для старта и кадров использовать Android Macrobenchmark (`StartupTimingMetric`, `FrameTimingMetric`) и Perfetto для поиска блокировок главного потока. Цели: отсутствие ANR, отсутствие ухудшения старта больше 10%, p95 `frameOverrunMs` не выше 0 на выбранном режиме Pixel 9. Сохранять исходные результаты, число итераций и параметры устройства. Сравнение debug и release недопустимо.

Фактические показатели Pixel 9 пока не измерены. Результаты не следует заменять оценкой плавности в эмуляторе.
